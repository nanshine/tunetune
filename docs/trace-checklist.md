# Trace 检查清单

用于评判新的 TuneTune 运行 trace，相当于 skill 的行为单元测试。每条记为“通过 / 未通过 / 不适用”，并附 trace 中的消息、工具调用或产物位置作为证据；Agent 自称完成不算证据。★ 为重点关注项。

## 一、安装与开场

1. ★ **安装走标准渠道，研究在当前目录，提示简洁。** 没装 skills 时按 INSTALL.md 用 `npx skills add` 或用户选的插件装到应用会发现的位置（通常是用户级），不另找发布包或自行拼装；已装好则不重复安装。随后用 skill 自带的 `scripts/init.py` 初始化当前目录，核对文件后直接读取 SKILL.md 继续。不擅自建研究子目录，不长篇解释为什么要检查技能列表，也不要求新开会话，除非确实找不到 skill。已有研究使用旧格式或绑定了其他版本工具时，`init.py` 会拒绝；Agent 用一句话说明原因和可选做法，不删除、覆盖 `.workspace/app/` 或绕过检查，也不照着模板手工拼出研究文件。
2. ★ **用的是预期的那一份 skill 和工具。** trace 里 skill 的 `Base directory` 来自预期渠道（如 DeepSeek Harness 插件目录，而不是更早留在 `~/.agents/skills` 的旧副本），项目 `.workspace/manifest.json` 的版本等于本次测试的发布版本。版本不对时，后面的面板、提示和流程都不能算作对当前版本的检验。
3. ★ **面板一开始就在应用里打开。** 初始化或继续研究后、开始调研前就打开面板，而不是等到提案确认时。装有 `dsh-tunetune` 插件时，Agent 不自己启动 `workspace.py`，右侧边栏自动打开这个研究的“模型研究室”，Agent 只告诉用户一次位置，不出现另开的 `127.0.0.1` 地址。Codex、Claude 桌面版用应用自带的浏览器视图显示面板地址（Codex 给可点击链接，启用 Browser 插件时由 Agent 打开）；没有侧边视图的应用用 `--open` 打开系统浏览器。
4. ★ **面向用户的语言。** 不出现“宿主”“技能选择器校验”这类内部术语，不以 skill、工作流、规则或文件作为提问理由，而是说出实际代价（下载、费用、数据外传、需要用户的判断）。先给结论或需要的决定；不复述用户已知的内容，不罗列“尚未完成”。限制说明只在会改变用户行动处说一次。长时间运行时只在情况有变化时发消息，不刷屏。

## 二、tunetune-init：需求与提案

5. ★ **交互以界定研究内容。** 问到会改变推荐的问题，先阅读已有材料再问关键缺口；不凑问题数量，也不把算法设计交给初学者。输出空间（类目、词表、格式）在提案阶段与用户定下。
6. ★ **调研真实发生，三个角色都考虑。** trace 中能看到按干预手段对照技术地图、用 `scout.py` 检索当前候选并核对许可与本机适配，提案里的链接不只是摆设。提案说明考虑过哪些干预类型、为何排除其余。方案包含可信基线、推荐路线、强质量参照或挑战路线（适用时提出 API）。
7. ★ **确认消息结构正确。** 说明要做什么、产出什么；按角色讲方案：每个角色测什么、为什么值得做、需要哪些资源；汇总资源（来源、预计下载和磁盘占用、存放位置、费用、数据是否外传）、预算和停止条件。资源以类别加上限表达（如公开权重下载总量、仅本地运行、不外传、API 花费上限）。在工作台打开提案并标记待确认（`records.py view --attention proposal:…`），附上已验证可打开的链接，在对话中一次请用户确认（DeepSeek Harness 插件下也可在工作台确认，回复会自动转给 Agent；Agent 此时用普通消息提问并结束本轮，而不是停在提问工具里）；用户回答后清除待确认标记，选项包括“全程推进”和“评测与基线就绪后先给我看”。需求提问阶段选过的资源边界（如“只用这台电脑”）不等于确认了方案。
8. ★ **提案只记方向。** 提案包含推荐、备选、有限预算、停止条件和交付形式。之后只在目标、推荐方向或范围变化时修改，不追加“本轮结果”“本轮修订”这类运行记录。
9. ★ **收集验收输入。** init 阶段收集几条用户想看到答案的真实输入，写入提案 `examples`，并作为 `comparison/inputs.jsonl` 的来源。用户手头没有材料时，Agent 可以提出注明来源的公开样例，随提案请用户认可，而不是悄悄自选。

## 三、授权与推进

10. ★ **确认后连续推进，只有一个固定停点。** 确认后直接准备资源，进入评测和实验，不在每个包、每次切换 skill 时重复请求批准。例行停顿只有主观参考答案审阅和用户自己选的检查点（如“评测与基线就绪后先给我看”），审阅期间继续准备资源、跑基线。
11. **边界内执行。** 只下载或调用已列出的资源，不超出已批准费用。API 密钥只通过环境变量或应用设置提供，不出现在对话、记录、快照或日志中。
12. ★ **积极收尾。** 每个阶段结束时，要么继续已授权的工作，要么提出一个具体决定并附推荐，要么完成交付；仍有差距时给出下一轮最有希望的方向、代价和推荐。不以“模型尚未完成、还缺……”这类缺失清单结束。

## 四、build-evaluation：可信测量

13. ★ **评测与模型解耦。** 评测通过 `TUNETUNE_TARGET` 调用被测模型的 `invoke.json`，再对输出打分。评测包里没有候选模型的提示词、推理代码或 `--method` 式方法切换；换方法不需要新版评测。
14. ★ **主观参考答案冻结前经用户审阅。** 审阅在工作台的“审阅参考答案”里逐条完成，不让用户去看本地文件。样本带 `reference_status`，`confirmed`/`corrected` 只来自用户的审阅；Agent 自己核对过的标注仍是 `draft`。用户明确把标注交给 Agent 时保持 `draft`，分数只称为“与草稿的一致程度”。不能出现参考资源仍为 `missing`、评测却已冻结并用于选交付的情况。
15. ★ **不过早冻结。** 覆盖检查、校准（正例、负例、取舍例）和端到端小测试在草稿阶段完成，用 `run.py --rehearse` 在基线上预演，预演结果不作为成绩报告。指标覆盖用户确认的整个输出（例如选了“框出人脸”就要给框的位置计分），未计分的部分写明是局限。基线已接近满分时，先补上目标里提到的难例，再比较方案或据此停止。冻结前完成覆盖检查；之后出新版本须有实际原因（需求变化、验收反馈等），并重测仍在比较的候选。冻结包中没有 `__pycache__` 或过时说明。
16. ★ **数据隔离真正执行。** 在依据材料设计规则、提示、类目或示例之前先划出最终检查集；用来设计方法的样本只算开发证据。 划分材料放在 `evaluation/` 的子目录（如 `evaluation/preparation/`）下，不在 `evaluation/` 根目录散放文件，用 `data_split` 固定内容哈希，训练输入确实排除留出集；近重复（裁剪、缩放、转载的同一张图或同一段文字）按内容或特征相似度检查，不只看文件名。抽查方式：留出样本在训练池里的最近邻相似度。不在根目录另建 holdout 文件。看过的样例不称为未见数据，留出集不具代表性时如实说明。方法的输出空间（词表、类目）来自用户确认的需求或全量材料，不从参考答案反推。

## 五、run-experiments：实验与交付

17. ★ **基线之后按轮次继续改进。** 基线 `e000` 在评测冻结前写好、作为端到端校准。之后每轮先调研证据，在 `plan.json` 写下 2–4 个实验（预留 `eNNN-slug` 编号、问题、预期观察、比较对象），再执行和复盘。实际评估推荐路线和质量参照，或用证据说明延期、排除；同一方法族停滞时换方法族，而不是反复小调参。`parent_experiment_id` 记录方法继承。执行或解析失败修复后用新编号重试同一计划项，不另开研究轮次。用户提出的方向或验收时的不满进入下一轮或新一版评测，并说明如何理解。
18. ★ **统一入口，走工具链。** 每个模型目录有 `invoke.json`。记录和执行使用项目内固定的 `.workspace/app/records.py`、`run.py` 等工具，而不是已安装 skill 里可能更新过的副本；执行通过 runner，结果用 `finalize` 发布。不出现从 `run.log` 拆结果、手写 status 或 outputs 的临时脚本。重试使用新编号。
19. ★ **交付对象经过评测。** 被选中交付的实验在当前评测下有成功测量，在最终检查集上测过一次，并在真实输入上验证加载和入口。不用查表或记住旧标签冒充模型能力，也不把 Agent 自己写的答案混进模型输出；新模型没有明显更好时保留原有模型。
20. ★ **验收在工作台展示。** 当前保留模型和有希望的候选都用 `run.py --compare` 跑验收输入，结果进入 `comparison/outputs.jsonl`，在工作台验收窗口查看，用户可自己点击重新运行或试新内容；不另写报告文件或使用脚本（如根目录的 `tools/predict_*.py`、`out/`）。
21. ★ **交付的是模型，不是应用。** 不问“是否写入博客”这类部署问题。最终报告说清达成效果、证据、不确定性、实际消耗和停止原因。

## 六、产物与清理

22. ★ **研究的全部占用都在项目内。** 环境在 `resources/`，pip、Hugging Face 缓存、自写辅助脚本和临时文件指向 `.workspace/cache/`、`.workspace/tmp/`，不写系统临时目录。根目录不放报告或说明文档。同一份权重不在多个实验中重复存放。复用全局已有模型时登记为资源，不向全局目录写入；项目外有写入时告诉用户位置和删除方法。用户级安装的 skills 不属于研究占用，但安装位置要在安装时说明。
23. **结论诚实。** 区分执行成功与质量合格、API 参照与私有本地交付、与草稿一致与符合用户偏好。缺失测量不当作 0。
