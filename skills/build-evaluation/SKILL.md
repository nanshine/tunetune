# 构建可执行评测

输入：已有格式 1 项目、目标及例子、资源、已有评测和用户授权范围。先读项目 `AGENTS.md` 的文件契约；检查 `project.json` 与 `.workspace/manifest.json` 格式兼容性，再读目标、资源、当前评测、候选、最近 review 和未处理反馈。依赖未就绪或多文件尚未写齐时暂停，不猜结果。

1. 明确要观察的行为、指标取舍、代表性案例和尚未覆盖的目标；保留来源。检查反馈绑定的 target_sha256，过时反馈先复核，不覆盖原始回答。需要用户判断时创建 `feedback/requests/<id>.json`，写 title、prompt、options 和关联文件/哈希，暂停依赖该答案的发布。
2. 在 `evaluation/draft/` 准备真实数据、评分规则、脚本及运行条件。`definition.json` 为 `{version,description,metrics:[{id,label,direction}],datasets:[],rubric?,command?}`，方向遵循 AGENTS。数据清单区分开发反馈与独立检查，记录来源、样例 ID、目标例子关联、处理过程、版本/哈希；已经用于调优的样例不再称为未见测试集。
3. 使用已有工具编写/复用必要评测与推理代码，不创建工作流 CLI 或 runner。实际试跑代表性输出，检查逐例分数、汇总算法、失败行为和规则是否表达用户要求。合成样例明确标识为合成，保留人工标注原文；不把计划或伪造分数当作试跑完成。
4. 在授权范围内将验证过的草稿复制到新的 `evaluation/versions/<version>/`。冻结数据、规则、代码及必要环境，附 SHA-256 或不可变来源；不能引用仍可修改的草稿作为版本内容。外部资源无法核验时明确阻塞。目录与版本永不复用或覆盖。
5. 校验该版本的完整文件、哈希和执行方式后，最后原子更新 `project.current_evaluation` 为具体版本。写入前重新读共享文件并检查哈希，遇到并发冲突停止合并，不静默覆盖。旧实验与旧评测不改写。
6. 采纳反馈的实际改动完成后再新增 `feedback/handled/`，记录 feedback_id、disposition、reason、changes；暂缓、不采用或追问也留理由，读取本身不算处理。

输出：可实际执行的评测版本路径、运行方式、试跑证据、指标含义和覆盖缺口；未发布时明确草稿/阻塞状态。新评测可对已有产物创建新 assessment，不要求重新训练，跨版分数分别解释。不要自动启动实验或修改研究空间界面。
